## Starting diagnosis

- **God objects.** `Player` is an abstract class with ~647 bare `public` fields. `Client extends Player` and is 1500+ lines on its own.
- **Hardcoded dispatch.** `PacketHandler`'s `PacketType[256]` table is the one good pattern in the codebase. Everything else — buttons, object actions, NPC actions, dialogues — is a giant `switch` in `ActionHandler`.
- **Hand-wired concurrency.** A single 600ms game tick loop in `Server`. Mina I/O threads hand packets to the game thread with almost no synchronisation.
- **Dead scripting layer.** Jython is on the classpath but `ScriptManager.loadScripts()` has no callers, so every `callFunc(...)` silently returns false and the 12 scripts in `Data/scripts/player/` never run.
- **No build metadata.** No Maven/Gradle, no dependency versions, no way to tell which of the ten jars in `deps/` are actually used.
- **Fragile persistence.** Flat-text save files with `[SECTION]` headers driving an `int ReadMode`, no schema version, non-atomic writes.

## Phase 3 — Data-driven dispatch

**Mechanics (decided with the user; applies to every cluster).** A cluster becomes a class holding the fields, and `Player` keeps **one** `public final` field for it, so a site reads `c.pos.selling` instead of `c.posSelling`. This is not the "delegating accessor" shape the step below originally described, and it is a deliberate choice: a Java field cannot delegate, so keeping old accessor *names* would mean rewriting every site to `c.getPosSelling()`/`c.setPosSelling(...)` and adding ~34 lines of boilerplate for this cluster alone, while making `Player` longer rather than shorter. The grouped shape is a 1:1 textual rewrite per site, drops the fields off `Player`, and gives the concept a home. **Encapsulation is a separate pass** — clusters start as public-field data bags so that a behaviour change cannot hide inside a large mechanical move.

**`build/purge/move-fields.js <cluster> <files...>`** was the tool for 4.1–4.6 and performs the rewrite for one cluster from a small per-cluster table in the script (longest old name first, so a short rule cannot clip a longer one; only ever after a `.`, so a bare local of the same name is left alone). [--apply]` or `... --fields server.game.players.Player .` from `Proxy Server/`. - ⚠️ **`startSmelting` dereferences `c.smelt.bar` with no null check**, right after `Bars.forType(...)`, which *can* return `null` — `getType` returns `""` for an out-of-range index and `forType("")` is `null`. ### 4.7 Position cluster ✅ DONE — the rewriter became type-aware

12 fields → `server/game/players/Position.java` (9) and `server/game/players/WalkRepath.java` (3), reached as `c.position` / `c.walkRepath`. **763 references across 42 files.** The twelve are the trio `absX`, `absY`, `heightLevel`; the walk cursor `currentX`/`currentY`; the map-region base `mapRegionX`/`mapRegionY`; the queued destination `teleportToX`/`teleportToY`; and the one-shot repath bookkeeping `lastWalkDestX`/`lastWalkDestY`/`walkRepathPending`. `Player.java` now declares **683** fields, twelve fewer than before the move (one per moved field).

**Why this one needed a different tool.** The previous six clusters were moved by `build/purge/move-fields.js`, which rewrites receiver-*qualified* uses and never touches bare ones. That fails here in both directions: `absX`, `absY` and `heightLevel` are declared on **`NPC`** as well (227 uses), and `PlayerAssistant` has its own public `absX`/`absY`/`heightLevel` (2 more), while `Region` and `WalkingCheck` have locals with those names and `Player.withinDistance(int absX, int getY, int getHeightLevel)` has parameters. Qualified-only would have left **281 bare references inside `Player.java`/`Client.java`** pointing at moved-away fields (no compile), and reaching bare names would have corrupted the `NPC` sites — a receiver-name skip list cannot express the difference, because **the type, not the name, is what distinguishes them**, and the same identifier (`n`) is an `NPC` in one file and a `Player` in another.

**The tool: `build/purge/typeaware/MoveFields.java`.** It attributes the whole of `src/` + `test/` with javac (the compiler API, not a parser — no new dependency) and rewrites an identifier only when `Trees.getElement` resolves it to a field *declared on `Player`*. It is not the "print the tree back" design the earlier estimate guessed: edits are character-range splices into the original text, so formatting, comments and line endings survive byte for byte and the diff is a clean 1:1 rewrite.

Three guards make the "silently wrong answer" failure mode impossible:
- **Unresolved symbols abort.** If javac reports any error while attributing, the run stops before collecting a single edit — because an unresolved identifier cannot be classified, and guessing would be exactly the `NPC`-corruption bug. (This caught a real setup problem on the first run: the tool's classpath had no JUnit, so the test sources failed to attribute and it refused to proceed rather than silently skipping them.)
- **Every splice is verified against the original text before it is written.** The range must contain exactly the identifier being replaced, and no two edits in a file may overlap. A mismatch aborts the whole run with nothing written.
- **A bare access in a static context is an error, not an edit.** Such an access could not have compiled today, so this is an assertion; it is there so that if it ever *does* fire, it fails loudly instead of emitting `position.absX` where `position` is unreachable.

**(1) The dry run and the classification.** 763 edits / 42 files, and the report is the proof the collision was handled: **325 `NPC` uses, 2 `PlayerAssistant` uses, 39 locals and 11 parameters left alone**, each labelled by what the name resolved to. The per-field counts (`absX` 243, `absY` 235, `heightLevel` 176, `teleportToX` 18, `teleportToY` 17, `mapRegionX`/`mapRegionY` 16 each, `currentX`/`currentY` 13 each, `lastWalkDestX`/`lastWalkDestY` 6 each, `walkRepathPending` 4) are all lower than the raw qualified counts measured last session (`absX` 268, `absY` 259, `heightLevel` 216, `teleportToX`/`teleportToY` 8 each, `mapRegionX`/`mapRegionY` 6 each, `lastWalkDestX`/`lastWalkDestY` 3 each) — and that is the point: the tool resolved each reference to its real owner instead of counting text, so a name that appears 268 times as `NPC.absX` and `Player.absX` combined is split correctly rather than guessed at.

**(2) The move.** `Player` keeps `public final Position position` and `public final WalkRepath walkRepath`; the twelve declarations were removed in a targeted, assert-then-write line edit that verified eight anchor lines by content before touching anything. `WalkRepath` was split out rather than folded into `Position` because a retry destination and a re-entry guard are not coordinates.

**(3) The verification that matters.** Re-running the tool on the moved tree reports **0 edits**, with the 763 references now resolving to `Position` (747) and `WalkRepath` (16) and the 325 `NPC` / 2 `PlayerAssistant` / 39 local / 11 parameter counts **unchanged**. A clean, idempotent, fully-accounted move: every reference that pointed at a `Player` field now points at the collaborator, and nothing else in the tree moved. Spot checks agree — `rg "position\.absX"` finds 198 sites, while the `npc.absX`/`n.absX`/`npcs[i].absX` forms are untouched in exactly the files that had them.

**(4) Defaults and persistence.** Every default is reproduced exactly, and two are load-bearing: `teleportToX`/`teleportToY` default to `-1` (readers test `-1` for "no teleport queued", so a `0` would look like a request to teleport to coordinate 0), and `lastWalkDestX`/`lastWalkDestY` likewise. Five of the twelve are persisted — `heightLevel` under save key `character-height`, and `absX`/`absY` under `character-posx`/`character-posy` — and all three keys are **string literals** in `PlayerSave`, so the path change cannot move them; the field names were kept identical anyway, per the 4.4 rule. `PlayerSaveTest` (updated by the tool's own run, 9 splices) covers the round trip.

**(5) `PositionTest` (5) pins the defaults, the `-1` sentinels, the repath defaults, per-player isolation, and that `getX()`/`getY()` still read through to `position.absX`/`absY`** — those two accessors already existed and are the seam the rest of the tree should migrate to. `getX()` having been written as `return absX` before the move is why the seam is worth pinning now. **206 tests green.**

⚠️ **Follow-up the pass revealed — Castle Wars barricade counts are `static`.** `saraBarricades`/`zammyBarricades` are `public static int`, so they are shared by every player, unlike the rest of the game's state. Not touched here (they are not position), but recorded because they are the same class of bug as `Music.unlocked` and the `Woodcutting.a` index fixed in 4.5.

⚠️ **27 of `Player`'s fields are `static`, and 21 of them are the skill-index constants** (`playerAttack` = 0 … `playerRunecrafting` = 20, used to index `playerLevel`/`playerXP`). They are *not* `final` and are `public`, but they are constants by intent and cannot move into a per-player collaborator — 4.8 must exclude them by name. The rest are the two `static final` limits (`maxPlayerListSize`, `maxNPCListSize`), the `playerProps` stream, `canLoadObjects`, and the two Castle Wars counters above.

**Measurement note.** The field counts in this section and the status block are now produced by `MoveFields --fields <type> .`, which counts references from the **attributed tree** and splits them into qualified and bare (and whole-type totals), instead of by the old textual `build/purge/player-field-usage.js`. That script was destroyed by a `gradlew clean` along with the rest of `build/purge`, which is why the tool carries the counter itself rather than depending on a separate script — and, after a *second* `clean` destroyed the type-aware version too, why it now lives at `Proxy Server/tools/typeaware/` outside `build/` (see the tooling note in the Phase 4 header). Going forward the numbers are the declared total, the non-static count, and the never-referenced count (currently 127), all reproducible from `MoveFields --fields`.

There were **no** collisions on `playerLevel`/`playerXP` at all (declared only on `Player`), so this cluster is the first where the collision was not a cross-type field but a same-named method.

**The cluster boundary was drawn at the table and its totals, and two neighbours were deliberately excluded:**
- **XP mechanics** — `lockedEXP` (persisted, key `lockedEXP`), `expModifier` (persisted, key `expModifier`) and the difficulty constants `EASY`/`NORMAL`/`HARD`/`EXTREME`. These are *how much* XP is awarded, not the table; moving `expModifier` without its four preset constants would split a concept across two classes.
- **Skilling-action state** — `playerSkilling[]`, `playerSkillProp[][]`, `stopPlayerSkill`, `checkSkilling[]`, `skillerPid`. These describe a gathering action in flight (the woodcutting/cooking "am I mid-swing" flags), which is the same family as the `WoodcuttingSession` in 4.5, not the level table.

**The skill-index constants stayed on `Player`, and they had to.** `playerAttack` = 0 … `playerRunecrafting` = 20 are `static`, so they cannot live on a per-player collaborator, yet they are the index space both arrays are read with (`skills.playerXP[Player.playerMagic]`). They are also, pre-existing, **not `final`** — a separate smudge left alone here. Because the coupling is now a cross-class one, `SkillsTest` pins it: all 21 constants are inside the array bounds and each equals its own index.

⚠️ **The defaults do not live in `Skills`, and that is deliberate.** A bare `new Skills()` is all zeros; the real starting table (level `1` in every slot, `10` hitpoints, `1300` hitpoints XP for the level-10 amount) is written by `Player`'s constructor, whose loop the tool rewrote to `skills.playerLevel[i]`. Seeding the collaborator instead would have been a behaviour change hiding inside a mechanical move, so `Player`'s constructor stays the single place that makes a new player well-formed — and `SkillsTest` asserts it from both ends: the bare object is zeros, and a `new Client(...)` has `playerLevel[3] == 10`, every other level `1`, `playerXP[3] == 1300` and the rest `0`.

**Persistence is a table, not a key.** `PlayerSave` writes an `[SKILLS]` section of `character-skill = <index> <level> <xp>` lines and reads it back the same way; both the section name and the key are string literals, so the path change cannot move them. Unlike every earlier cluster there was no single save key to grep for, which is worth knowing for the next pass.

`totalLevel`/`xpTotal` are **dead** — each is written once in `Client.initialize()` and never read (the quest tab and `AchievementBroadcast` call `getPA().totalLevel()` instead). Brought along so the skills concept lives in one place and marked deletable, the same call as `BountyHunterState.bountyIcon` in 4.6.

### 4.9 Appearance cluster ✅ DONE — and a surgery bug worth recording

6 fields → `server/game/players/Appearance.java`, reached as `c.appearance`: the appearance slots `playerAppearance`, the dirty flag `appearanceUpdateRequired`, `canChangeAppearance`, and the three overhead icons `headIcon` (prayer/curse), `headIconPk` (PK skull), `headIconHints` (duel). **97 references across 16 files.** `Player.java` **680 → 675** declared fields.

**Boundary.** Kept out on purpose: `playerName` (**254 refs — identity, not appearance**), the chat-text family (`chatText`, `chatTextColor`, `chatTextEffects`, `chatTextSize`, `chatTextUpdateRequired`, `forcedChatUpdateRequired` — what a player is *saying*), and ⚠️ **`playerProps`** (49 bare refs), which is `protected static Stream` on `Player` — one shared scratch buffer used to serialise whichever player's appearance block is being written, not per-player state. It stays with the serialiser and joins `Music.unlocked` and the Castle Wars counters on the list of shared-static hazards.

**Two defaults are load-bearing.** `appearanceUpdateRequired` starts `true` — a login whose flag were `false` would render with no appearance until something else forced an update. And both head icons start at **`-1`, not `0`**: `headIconPk = 0` is a real PK skull and `headIcon = 0` a real prayer icon, so a `0` default would paint an icon on every player. `AppearanceTest` pins the sentinel separately for that reason.

**The tool handled two more shapes correctly.** First, `headIcon` is a strict prefix of `headIconPk` and `headIconHints`, and the tool matches identifiers *exactly*, so there is no ordering hazard at all — the "longest name first" rule the old regex rewriter needed cannot bite here. Second, a getter/setter pair takes a parameter that shadows the field: `this.appearance.appearanceUpdateRequired = appearanceUpdateRequired;` came out with the field rewritten and **the parameter left alone**, which is one of the two parameters the dry run reported.

⚠️ **A surgery bug I introduced and caught: I clobbered `public int apset;`.** The declaration removal asserted the anchor at line 944 (`public int playerAppearance[] = new int[13];`) and then wrote to *both* index 943 and index 944 — but index 944 was line 945, `public int apset;`, which had never been asserted, so it was silently overwritten by the new collaborator field. **The compiler caught it**: `apset` is assigned in `Player`'s constructor and its declaration was gone, so compilation would have failed. Restored by re-adding the missing declaration, after which everything compiles and all 216 tests pass. **The lesson is the general one: a line-index surgery must only ever write to indices whose current content it has already verified** — asserting "the line I intend to replace" is not enough when a replacement spans more indices than the anchor check covered. Every earlier cluster got this right by accident because each replacement was a single line; this is the first that wrote two, and it is the first that broke. The declaration-removal step for later clusters should assert *every* index it writes, not just the first.

**The slots are seeded by `Player`'s constructor, not by `Appearance`** (gender 0, head 7, torso 25, … as before), so as with `Skills` the test asserts both ends: a bare `new Appearance()` is 13 zeros, a new player is not. **Persistence is an `[LOOK]` table** of `character-look = <index> <value>` lines — note that grepping `PlayerSave` for `appearance` finds *nothing*, because the key is `character-look`; the other five fields are session state and are not saved at all.

Re-running the tool reports **0 edits** (all three of position, skills and appearance now verify clean). `AppearanceTest` (5): a bare object's defaults, the `-1` sentinel, the constructor's seeded slots, the dirty flag on a fresh player, and that two players share neither the object nor the slot array. **216 tests green.**

### 4.10 Timers sub-slice ✅ DONE — the first pass with no collisions at all

**Eighteen fields, not thirty-three.** The plan's §4.10 called the whole timer set "the last big one", and on measuring it that is true (about 33 fields) but also *not worth doing in one pass*: the fields are declared in **giant comma-lists mixed with non-timers** (line 332 alone held fifteen of them alongside `lastPoison`, `lastYell`, `reduceStat` and `specDelay = System.currentTimeMillis()`), and several are not the same shape as the rest. So the subset taken here is the **pure `*Delay` availability clocks** — the "may I do X again yet?" set — and the duration/scheduling timers were left for the combat pass.

18 fields → `server/game/players/Timers.java`, reached as `c.timers`: `foodDelay`, `potDelay`, `alchDelay`, `teleBlockDelay`, `godSpellDelay`, `reduceSpellDelay`, `ssDelay`, `clawDelay`, `buryDelay`, `dfsDelay`, `protMageDelay`, `protMeleeDelay`, `protRangeDelay`, `duelDelay`, `logoutDelay`, `teleGrabDelay`, `singleCombatDelay`, `singleCombatDelay2`. **112 references across 17 files.** `Player.java` **675 → 658** declared fields.

**This is the first cluster the rewriter reported with an empty "left alone" list** — no cross-type collisions, no shadowing locals, no same-named methods, and every one of the 112 sites already had a receiver. After position (NPC/PlayerAssistant/local/parameter collisions), skills (methods and a local) and appearance (parameters), it is worth noting that the *absence* of a complication is itself a measurement, not an assumption.

**Three different shapes are hiding under one `Delay` suffix**, which is why they were checked one at a time:
- **Fifteen are "last used" epoch-millisecond stamps**, read against the clock as `System.currentTimeMillis() - X > threshold` (available) or `< threshold` (cooling down) — e.g. `now - foodDelay > 2000` in `PlayerAssistant`, `now - logoutDelay > 10000` in `PlayerHandler`. Note `foodDelay` is not food-only: `Agility.doWildernessEntrance` reads the same field as a general 2s obstacle cooldown (`now - foodDelay < 2000` = "still cooling down") and sets it, and `Potions` copies `potDelay` into it, so eating, drinking and agility share one clock.
- ⚠️ **Two are not timestamps at all — and I first miscounted this as one.** `clawDelay` is a small tick countdown: `= 2` when claws activate, decremented once per tick in `Client`, `> 0` meaning "claws active"; it happens to live in the same declaration list and sort next to `clawDamage`. `ssDelay` is *also* a countdown and was initially filed here under the stamps: it is **Soul Split** (curse `curseActive[18]`), set to `4` on a soul-split hit in `Curse` and decremented in `Curse.handleProcess()`, with `> 0` gating a repeat trigger. Neither is read against `System.currentTimeMillis()` — they are counters, not clocks, and `ssDelay` being a `long` is no help in telling them apart.
- ⚠️ **`reduceSpellDelay` is a `long[6]` table**, one stamp per reduce-spell slot indexed by `reduceSpellId` and compared against `REDUCE_SPELL_TIME`. It was declared on its own line, which made it the easiest of the eighteen to move.
- ⚠️ **`teleGrabDelay` is write-only, a pre-existing loose end the move made visible.** It is set in `MagicOnFloorItems` when a telekinetic grab lands, but no read of it exists anywhere in the tree (checked by grepping the whole `Proxy Server`), so the intended tele-grab spam cooldown was never wired up. It moved with the cluster unchanged; adding the gate would be a behaviour change and is deliberately not done here. My first version of `TimersTest` asserted `now - teleGrabDelay > 0` as "the exact comparison the code uses" — there is no comparison, so that assertion was removed rather than kept as a vacuous pass.

**Every default is `0`, and the whole cluster depends on it.** For the fifteen stamps `0` means "never used", so `now - 0` exceeds any threshold and a new player can eat, alch, bury and tele-grab immediately; the same value is the *reset sentinel* (`c.timers.teleBlockDelay = 0;` clears a teleblock) and the only value meaning "claws off" or "Soul Split idle". A non-zero default would silently lock new players out of most actions, so `TimersTest` **reflects over the class** and asserts every non-static field is zero (and the array is six zeroed slots), with a count guard so the loop cannot pass vacuously — that way a field added later with a non-zero default fails the test rather than shipping.

⚠️ **`teleBlockDelay` is split from its sibling `teleBlockLength`, and that is left as a known wart.** The stamp moved here; the duration it is compared against (`now - teleBlockDelay < teleBlockLength`) stayed on `Player` with the other durations and should be reunited in the combat pass. Its save-path treatment is also unusual and was checked before moving: `PlayerSave` matches `token.equals("teleblock-length")` and then sets `teleBlockDelay = System.currentTimeMillis()` alongside `teleBlockLength = ...`, so **the on-disk key belongs to `teleBlockLength` and the delay is derived at load — no save key moved**, and `PlayerSave` has no key for the delay to preserve.

Deliberately left on `Player` with this pass, each for a reason: `specDelay` (its initialiser is `System.currentTimeMillis()`, so it is not the same shape and would have broken the all-zero invariant), `restoreStatsDelay`, `poisonDelay`, `teleTimer`, `respawnTimer`, `saveTimer`, `teleBlockLength`, and `skullTimer` (the one persisted timer — it has a save key, so it needs the save-path treatment rather than a rename).

⚠️ **The declaration surgery was done by exact literal replacement with a uniqueness check, not by line index — the §4.9 lesson applied, and it is the first surgery pass with nothing clobbered.** Four edits: the fifteen-name comma-list on line 332 (rewritten in place, keeping `specDelay`, `reduceStat` and `restoreStatsDelay`), `clawDelay` and `ssDelay` (each the *first* declarator in its own list, so they needed `NAME, ` removed rather than `, NAME`), and the standalone `reduceSpellDelay` line deleted. All names were verified absent from `Player`'s declarations afterwards, and the collaborator field was placed at the old timer block.

`TimersTest` (5): the reflective all-zero-defaults invariant, a new player being immediately able to use every delayed action (asserted against the *actual comparisons* the code uses, including the not-teleblocked case), both countdowns (claws and Soul Split) being idle, the reduce-spell table matching `REDUCE_SPELLS`/`REDUCE_SPELL_TIME` in length, and that two players share neither the object nor the array. Re-running the tool reports **0 edits**, and the other three clusters still report 0 each. **221 tests green.**

## Phase 5 — Concurrency and service lifecycle

- **Replace the hand-wired tick loop** with a proper scheduler. `CycleEvent`/`CycleEventContainer`/`CycleEventHandler` already exists and coexists with the manual `process()` calls in `PlayerHandler` — consolidate on one.
- **Make the Mina↔game-thread boundary explicit.** Phase 0 fixed the two worst races; the general rule (I/O threads enqueue, game thread drains) should be enforced by the types, not by convention.
- **Ordering guarantee.** `PlayerHandler.process()` currently documents its per-player order in a comment (`packets → process → merge walk → step → follow+swing`). That order is load-bearing and undocumented in code; encode it.
- **Shutdown.** `destruct()`/`removePlayer()` and the update-kick path should be a single well-defined lifecycle, so a shutdown always saves everyone exactly once.

## Phase 6 — Persistence and configuration

- **Externalise configuration.** `Config` is compile-time constants; credentials are hardcoded in source (`Server.java`'s `MainLoader` construction, `HiscoresHandler`'s IP/DB/user/pass). Move to a properties file that is gitignored, with a checked-in template.
- **Fix the database layer.** `HiscoresHandler`'s `con`/`stmt` are `public static`, never pooled, never closed. Introduce a connection pool.
- **Password storage.** Save files hold unsalted `Misc.md5Hash(playerPass)` in plaintext, with a three-way legacy fallback on load accepting plaintext or `basicEncrypt`. Migrate to a salted hash (bcrypt/argon2) with a lazy upgrade path on login.
- **Save-file format.** Add a schema version header. Consider moving to a real format (JSON/SQLite) behind the same `PlayerSave` API, with a one-time importer from the flat-text files.
- **Charset.** `FileWriter` uses the platform default. Pin to UTF-8 explicitly — deliberately left out of Phase 0 because it changes output bytes.
