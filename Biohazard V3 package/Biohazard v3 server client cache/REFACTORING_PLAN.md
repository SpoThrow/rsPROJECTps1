**Last thing I did:** **The periodic save, which turned out not to exist.** Phase 5 exposed that `PlayerSaving.initialize()` had no callers, so the five-minute loop its whole design implied had **never run** — meaning a crash or hard kill lost every change since each player last logged out, and the Phase 5 shutdown hook only covered a clean stop. Rather than resurrect the dead class as written, I replaced it: the original design was actively dangerous (**it saved every player in a burst from its own background thread, reading live game state while the tick mutated it, and racing the logout path on the same client's file**). The new `PlayerSaving` is driven from `Server.tick()` and writes **at most one character per tick**, so there are no locks, no races and no burst — at 600 ms a tick that is under two writes a second even with a full realm, and it runs last in the tick so it never sees a player mid-update. ⚠️ **The cost is deliberate and worth stating: a character write now happens on the tick thread, so a slow disk delays that one tick** — which is exactly why it is one character per tick and not a batch. ⚠️ **The trap the design had to avoid, and the test that pins it: the autosave must not latch `Client.saveCharacterOnce()`'s once-guard.** If it did, the logout that followed would skip its save and the player would silently lose up to five minutes — a bug that reads as "the last few minutes don't stick" and would be miserable to trace. `PlayerSavingTest.anAutosaveDoesNotConsumeTheFinalLogoutSave` asserts the autosave leaves the flag alone *and* that the later logout's newer state is what ends up on disk; an autosave followed by a logout therefore writes twice, on purpose. ## Starting diagnosis

- **God objects.** `Player` is an abstract class with ~647 bare `public` fields. `Client extends Player` and is 1500+ lines on its own.
- **Hardcoded dispatch.** `PacketHandler`'s `PacketType[256]` table is the one good pattern in the codebase. Everything else — buttons, object actions, NPC actions, dialogues — is a giant `switch` in `ActionHandler`.
- **Hand-wired concurrency.** A single 600ms game tick loop in `Server`. Mina I/O threads hand packets to the game thread with almost no synchronisation.
- **Dead scripting layer.** Jython is on the classpath but `ScriptManager.loadScripts()` has no callers, so every `callFunc(...)` silently returns false and the 12 scripts in `Data/scripts/player/` never run.
- **No build metadata.** No Maven/Gradle, no dependency versions, no way to tell which of the ten jars in `deps/` are actually used.
- **Fragile persistence.** Flat-text save files with `[SECTION]` headers driving an `int ReadMode`, no schema version, non-atomic writes.

**Package convention** (settled by the two migrations above): the registry lives with the dispatcher that consults it. ### 4.7 Position cluster ✅ DONE — the rewriter became type-aware

12 fields → `server/game/players/Position.java` (9) and `server/game/players/WalkRepath.java` (3), reached as `c.position` / `c.walkRepath`. **763 references across 42 files.** The twelve are the trio `absX`, `absY`, `heightLevel`; the walk cursor `currentX`/`currentY`; the map-region base `mapRegionX`/`mapRegionY`; the queued destination `teleportToX`/`teleportToY`; and the one-shot repath bookkeeping `lastWalkDestX`/`lastWalkDestY`/`walkRepathPending`. `Player.java` now declares **683** fields, twelve fewer than before the move (one per moved field).

**Why this one needed a different tool.** The previous six clusters were moved by `build/purge/move-fields.js`, which rewrites receiver-*qualified* uses and never touches bare ones. That fails here in both directions: `absX`, `absY` and `heightLevel` are declared on **`NPC`** as well (227 uses), and `PlayerAssistant` has its own public `absX`/`absY`/`heightLevel` (2 more), while `Region` and `WalkingCheck` have locals with those names and `Player.withinDistance(int absX, int getY, int getHeightLevel)` has parameters. Qualified-only would have left **281 bare references inside `Player.java`/`Client.java`** pointing at moved-away fields (no compile), and reaching bare names would have corrupted the `NPC` sites — a receiver-name skip list cannot express the difference, because **the type, not the name, is what distinguishes them**, and the same identifier (`n`) is an `NPC` in one file and a `Player` in another.

**The tool: `build/purge/typeaware/MoveFields.java`.** It attributes the whole of `src/` + `test/` with javac (the compiler API, not a parser — no new dependency) and rewrites an identifier only when `Trees.getElement` resolves it to a field *declared on `Player`*. It is not the "print the tree back" design the earlier estimate guessed: edits are character-range splices into the original text, so formatting, comments and line endings survive byte for byte and the diff is a clean 1:1 rewrite.

Three guards make the "silently wrong answer" failure mode impossible:
- **Unresolved symbols abort.** If javac reports any error while attributing, the run stops before collecting a single edit — because an unresolved identifier cannot be classified, and guessing would be exactly the `NPC`-corruption bug. (This caught a real setup problem on the first run: the tool's classpath had no JUnit, so the test sources failed to attribute and it refused to proceed rather than silently skipping them.)
- **Every splice is verified against the original text before it is written.** The range must contain exactly the identifier being replaced, and no two edits in a file may overlap. A mismatch aborts the whole run with nothing written.
- **A bare access in a static context is an error, not an edit.** Such an access could not have compiled today, so this is an assertion; it is there so that if it ever *does* fire, it fails loudly instead of emitting `position.absX` where `position` is unreachable.

**(1) The dry run and the classification.** 763 edits / 42 files, and the report is the proof the collision was handled: **325 `NPC` uses, 2 `PlayerAssistant` uses, 39 locals and 11 parameters left alone**, each labelled by what the name resolved to. The per-field counts (`absX` 243, `absY` 235, `heightLevel` 176, `teleportToX` 18, `teleportToY` 17, `mapRegionX`/`mapRegionY` 16 each, `currentX`/`currentY` 13 each, `lastWalkDestX`/`lastWalkDestY` 6 each, `walkRepathPending` 4) are all lower than the raw qualified counts measured last session (`absX` 268, `absY` 259, `heightLevel` 216, `teleportToX`/`teleportToY` 8 each, `mapRegionX`/`mapRegionY` 6 each, `lastWalkDestX`/`lastWalkDestY` 3 each) — and that is the point: the tool resolved each reference to its real owner instead of counting text, so a name that appears 268 times as `NPC.absX` and `Player.absX` combined is split correctly rather than guessed at.

**(2) The move.** `Player` keeps `public final Position position` and `public final WalkRepath walkRepath`; the twelve declarations were removed in a targeted, assert-then-write line edit that verified eight anchor lines by content before touching anything. `WalkRepath` was split out rather than folded into `Position` because a retry destination and a re-entry guard are not coordinates.

**(3) The verification that matters.** Re-running the tool on the moved tree reports **0 edits**, with the 763 references now resolving to `Position` (747) and `WalkRepath` (16) and the 325 `NPC` / 2 `PlayerAssistant` / 39 local / 11 parameter counts **unchanged**. A clean, idempotent, fully-accounted move: every reference that pointed at a `Player` field now points at the collaborator, and nothing else in the tree moved. Spot checks agree — `rg "position\.absX"` finds 198 sites, while the `npc.absX`/`n.absX`/`npcs[i].absX` forms are untouched in exactly the files that had them.

**(4) Defaults and persistence.** Every default is reproduced exactly, and two are load-bearing: `teleportToX`/`teleportToY` default to `-1` (readers test `-1` for "no teleport queued", so a `0` would look like a request to teleport to coordinate 0), and `lastWalkDestX`/`lastWalkDestY` likewise. Five of the twelve are persisted — `heightLevel` under save key `character-height`, and `absX`/`absY` under `character-posx`/`character-posy` — and all three keys are **string literals** in `PlayerSave`, so the path change cannot move them; the field names were kept identical anyway, per the 4.4 rule. `PlayerSaveTest` (updated by the tool's own run, 9 splices) covers the round trip.

**(5) `PositionTest` (5) pins the defaults, the `-1` sentinels, the repath defaults, per-player isolation, and that `getX()`/`getY()` still read through to `position.absX`/`absY`** — those two accessors already existed and are the seam the rest of the tree should migrate to. `getX()` having been written as `return absX` before the move is why the seam is worth pinning now. **206 tests green.**

⚠️ **Follow-up the pass revealed — Castle Wars barricade counts are `static`.** `saraBarricades`/`zammyBarricades` are `public static int`, so they are shared by every player, unlike the rest of the game's state. Not touched here (they are not position), but recorded because they are the same class of bug as `Music.unlocked` and the `Woodcutting.a` index fixed in 4.5.

⚠️ **27 of `Player`'s fields are `static`, and 21 of them are the skill-index constants** (`playerAttack` = 0 … `playerRunecrafting` = 20, used to index `playerLevel`/`playerXP`). They are *not* `final` and are `public`, but they are constants by intent and cannot move into a per-player collaborator — 4.8 must exclude them by name. ### 4.9 Appearance cluster ✅ DONE — and a surgery bug worth recording

6 fields → `server/game/players/Appearance.java`, reached as `c.appearance`: the appearance slots `playerAppearance`, the dirty flag `appearanceUpdateRequired`, `canChangeAppearance`, and the three overhead icons `headIcon` (prayer/curse), `headIconPk` (PK skull), `headIconHints` (duel). **97 references across 16 files.** `Player.java` **680 → 675** declared fields.

It stays with the serialiser and joins `Music.unlocked` and the Castle Wars counters on the list of shared-static hazards.

**Two defaults are load-bearing.** `appearanceUpdateRequired` starts `true` — a login whose flag were `false` would render with no appearance until something else forced an update. And both head icons start at **`-1`, not `0`**: `headIconPk = 0` is a real PK skull and `headIcon = 0` a real prayer icon, so a `0` default would paint an icon on every player. `AppearanceTest` pins the sentinel separately for that reason.

**The tool handled two more shapes correctly.** First, `headIcon` is a strict prefix of `headIconPk` and `headIconHints`, and the tool matches identifiers *exactly*, so there is no ordering hazard at all — the "longest name first" rule the old regex rewriter needed cannot bite here. Second, a getter/setter pair takes a parameter that shadows the field: `this.appearance.appearanceUpdateRequired = appearanceUpdateRequired;` came out with the field rewritten and **the parameter left alone**, which is one of the two parameters the dry run reported.

⚠️ **A surgery bug I introduced and caught: I clobbered `public int apset;`.** The declaration removal asserted the anchor at line 944 (`public int playerAppearance[] = new int[13];`) and then wrote to *both* index 943 and index 944 — but index 944 was line 945, `public int apset;`, which had never been asserted, so it was silently overwritten by the new collaborator field. **The compiler caught it**: `apset` is assigned in `Player`'s constructor and its declaration was gone, so compilation would have failed. Restored by re-adding the missing declaration, after which everything compiles and all 216 tests pass. **The lesson is the general one: a line-index surgery must only ever write to indices whose current content it has already verified** — asserting "the line I intend to replace" is not enough when a replacement spans more indices than the anchor check covered. The declaration-removal step for later clusters should assert *every* index it writes, not just the first.

**The slots are seeded by `Player`'s constructor, not by `Appearance`** (gender 0, head 7, torso 25, … as before), so as with `Skills` the test asserts both ends: a bare `new Appearance()` is 13 zeros, a new player is not. **Persistence is an `[LOOK]` table** of `character-look = <index> <value>` lines — note that grepping `PlayerSave` for `appearance` finds *nothing*, because the key is `character-look`; the other five fields are session state and are not saved at all.

Re-running the tool reports **0 edits** (all three of position, skills and appearance now verify clean). `AppearanceTest` (5): a bare object's defaults, the `-1` sentinel, the constructor's seeded slots, the dirty flag on a fresh player, and that two players share neither the object nor the slot array. **216 tests green.**

### 4.10 Timers sub-slice ✅ DONE — the first pass with no collisions at all

**Eighteen fields, not thirty-three.** The plan's §4.10 called the whole timer set "the last big one", and on measuring it that is true (about 33 fields) but also *not worth doing in one pass*: the fields are declared in **giant comma-lists mixed with non-timers** (line 332 alone held fifteen of them alongside `lastPoison`, `lastYell`, `reduceStat` and `specDelay = System.currentTimeMillis()`), and several are not the same shape as the rest. So the subset taken here is the **pure `*Delay` availability clocks** — the "may I do X again yet?" set — and the duration/scheduling timers were left for the combat pass.

18 fields → `server/game/players/Timers.java`, reached as `c.timers`: `foodDelay`, `potDelay`, `alchDelay`, `teleBlockDelay`, `godSpellDelay`, `reduceSpellDelay`, `ssDelay`, `clawDelay`, `buryDelay`, `dfsDelay`, `protMageDelay`, `protMeleeDelay`, `protRangeDelay`, `duelDelay`, `logoutDelay`, `teleGrabDelay`, `singleCombatDelay`, `singleCombatDelay2`. **112 references across 17 files.** `Player.java` **675 → 658** declared fields.

**This is the first cluster the rewriter reported with an empty "left alone" list** — no cross-type collisions, no shadowing locals, no same-named methods, and every one of the 112 sites already had a receiver. After position (NPC/PlayerAssistant/local/parameter collisions), skills (methods and a local) and appearance (parameters), it is worth noting that the *absence* of a complication is itself a measurement, not an assumption.

**Three different shapes are hiding under one `Delay` suffix**, which is why they were checked one at a time:
- **Fifteen are "last used" epoch-millisecond stamps**, read against the clock as `System.currentTimeMillis() - X > threshold` (available) or `< threshold` (cooling down) — e.g. `now - foodDelay > 2000` in `PlayerAssistant`, `now - logoutDelay > 10000` in `PlayerHandler`. Note `foodDelay` is not food-only: `Agility.doWildernessEntrance` reads the same field as a general 2s obstacle cooldown (`now - foodDelay < 2000` = "still cooling down") and sets it, and `Potions` copies `potDelay` into it, so eating, drinking and agility share one clock.
- ⚠️ **Two are not timestamps at all — and I first miscounted this as one.** `clawDelay` is a small tick countdown: `= 2` when claws activate, decremented once per tick in `Client`, `> 0` meaning "claws active"; it happens to live in the same declaration list and sort next to `clawDamage`. `ssDelay` is *also* a countdown and was initially filed here under the stamps: it is **Soul Split** (curse `curseActive[18]`), set to `4` on a soul-split hit in `Curse` and decremented in `Curse.handleProcess()`, with `> 0` gating a repeat trigger. Neither is read against `System.currentTimeMillis()` — they are counters, not clocks, and `ssDelay` being a `long` is no help in telling them apart.
- ⚠️ **`reduceSpellDelay` is a `long[6]` table**, one stamp per reduce-spell slot indexed by `reduceSpellId` and compared against `REDUCE_SPELL_TIME`. It was declared on its own line, which made it the easiest of the eighteen to move.
- ⚠️ **`teleGrabDelay` is write-only, a pre-existing loose end the move made visible.** It is set in `MagicOnFloorItems` when a telekinetic grab lands, but no read of it exists anywhere in the tree (checked by grepping the whole `Proxy Server`), so the intended tele-grab spam cooldown was never wired up. It moved with the cluster unchanged; adding the gate would be a behaviour change and is deliberately not done here. My first version of `TimersTest` asserted `now - teleGrabDelay > 0` as "the exact comparison the code uses" — there is no comparison, so that assertion was removed rather than kept as a vacuous pass.

**Every default is `0`, and the whole cluster depends on it.** For the fifteen stamps `0` means "never used", so `now - 0` exceeds any threshold and a new player can eat, alch, bury and tele-grab immediately; the same value is the *reset sentinel* (`c.timers.teleBlockDelay = 0;` clears a teleblock) and the only value meaning "claws off" or "Soul Split idle". A non-zero default would silently lock new players out of most actions, so `TimersTest` **reflects over the class** and asserts every non-static field is zero (and the array is six zeroed slots), with a count guard so the loop cannot pass vacuously — that way a field added later with a non-zero default fails the test rather than shipping.

⚠️ **`teleBlockDelay` is split from its sibling `teleBlockLength`, and that is left as a known wart.** The stamp moved here; the duration it is compared against (`now - teleBlockDelay < teleBlockLength`) stayed on `Player` with the other durations and should be reunited in the combat pass. Its save-path treatment is also unusual and was checked before moving: `PlayerSave` matches `token.equals("teleblock-length")` and then sets `teleBlockDelay = System.currentTimeMillis()` alongside `teleBlockLength = ...`, so **the on-disk key belongs to `teleBlockLength` and the delay is derived at load — no save key moved**, and `PlayerSave` has no key for the delay to preserve.

Deliberately left on `Player` with this pass, each for a reason: `specDelay` (its initialiser is `System.currentTimeMillis()`, so it is not the same shape and would have broken the all-zero invariant), `restoreStatsDelay`, `poisonDelay`, `teleTimer`, `respawnTimer`, `saveTimer`, `teleBlockLength`, and `skullTimer` (the one persisted timer — it has a save key, so it needs the save-path treatment rather than a rename).

⚠️ **The declaration surgery was done by exact literal replacement with a uniqueness check, not by line index — the §4.9 lesson applied, and it is the first surgery pass with nothing clobbered.** Four edits: the fifteen-name comma-list on line 332 (rewritten in place, keeping `specDelay`, `reduceStat` and `restoreStatsDelay`), `clawDelay` and `ssDelay` (each the *first* declarator in its own list, so they needed `NAME, ` removed rather than `, NAME`), and the standalone `reduceSpellDelay` line deleted. All names were verified absent from `Player`'s declarations afterwards, and the collaborator field was placed at the old timer block.

`TimersTest` (5): the reflective all-zero-defaults invariant, a new player being immediately able to use every delayed action (asserted against the *actual comparisons* the code uses, including the not-teleblocked case), both countdowns (claws and Soul Split) being idle, the reduce-spell table matching `REDUCE_SPELLS`/`REDUCE_SPELL_TIME` in length, and that two players share neither the object nor the array. Re-running the tool reports **0 edits**, and the other three clusters still report 0 each. **221 tests green.**

⚠️ **Two of the six are write-only, and that is a real finding.** `usingPrayer` is recomputed `true`/`false` in `getPrayerDelay` and `handlePrayerDrain` but **never read** (all 5 references are assignments), and `prayerId` is assigned `-1` in `reducePrayerLevel` and **never read** (its single reference). **Where the boundary was drawn, and why.** The combat pass overlaps prayer, so this pass took only the mutable prayer state and left two things behind on purpose:

The cost is that the index spaces are now split across two classes, so `PrayersTest` pins each array's length against the table that indexes it (26 for prayers, 20 for curses) — a mismatch there is an out-of-bounds waiting to happen.
- **The zero-reference `prayerDelay`**, which stayed on `Player` as a dead field (§4.11 finding).

`PrayersTest` (4): the load-bearing defaults (`1.0`, `-1`, zero, off, all flags false), the four cross-class index-space checks per book, a fresh player not being blocked from toggling (`now - stopPrayerDelay >= 5000`), and per-player ownership of both arrays and both scalars. Re-running the tool reports **0 edits for all five clusters**, and `--fields` reports `declared fields : 641`. **226 tests green.**

⚠️ **Combat meta is now all but done.** §4.12 took the prayer/curse half, §4.13 the special-attack half, and §4.14–§4.15 the attack-mode/magic bucket — all four measured to be **collision-free** (no other type declares any of their names, so the skips were shadowing locals/parameters and nothing else). ### 4.15 The magic state ✅ DONE — and the measurement was wrong twice

**Seven fields → `MagicState`** (`c.magic`): `playerMagicBook`, `autocastId`, `autocastMemWeapon`, `autocastMemSpell`, `autocastMemBook`, `spellId`, `oldSpellId`. **182 references across 12 files** (`CombatAssistant` 80, `PlayerAssistant` 17, `CastleWars` 12, `ActionHandler` 7, `AttackPlayer` 6, `ClickingButtons` 5, `PlayerSave` 5, `ClickNPC` 3, `OwnerCommands` 3, ...). `Player.java` **629 → 624** declared fields (**597** non-static).

### 4.16 The targeting pointers ✅ DONE — and the rewriter had a real bug

**Nine fields → `Targeting`** (`c.targeting`): `playerIndex`, `npcIndex`, `oldPlayerIndex`, `oldNpcIndex`, `killingNpcIndex`, `underAttackBy`, `underAttackBy2`, `ssTarget`, `ssTargetNpc`. **283 references across 16 files** (`CombatAssistant` 143, `ClickNPC` 27, `AttackPlayer` 21, `Client` 18, `NPCHandler` 15, `Curse` 14, `PlayerAssistant` 13, `DwarfCannon` 9, `Walking` 9, ...). `Player.java` **624 → 616** declared fields (**589** non-static, still **27** static).

The bag holds **both directions of a fight** — the target this player has selected, and the attacker who has selected them — because the multi-combat checks read the two together (`c.targeting.underAttackBy > 0 || c.targeting.underAttackBy2 > 0`). `ssTarget`/`ssTargetNpc` are **Soul Split's** current player/NPC target (`Curse` writes one and zeroes the other, then re-reads both at the heal step), so the curse's target sits with the weapon's. `ssHeal` deliberately **stayed on `Player`**: it is the heal *amount*, not a target.

**⚠️ `underAttackBy` is the first field that genuinely exists on another type.** §4.11's `freezeTimer`/`attackTimer` were `NPC` fields too, but this is the same idea *from the other side*: on a player it is the index of whoever is attacking them, on an `NPC` it is the mirror. `NPC.java` line 32 declares it, and `NPCHandler` interleaves both in adjacent statements (`npcs[i].underAttackBy > 0` at 4160, `c.targeting.underAttackBy2 = i` at 4217, `npcs[i].underAttackBy = 0` at 2880). The dry run separated them correctly — **11 `NPC` references left alone and 18 parameters**, with `javac : 0 errors while attributing` — so this is the collision pattern working as intended rather than a shadowing accident. Every other field in the cluster is declared only on `Player`.

**⚠️ The rewriter had a real bug, and the compiler found exactly one instance of it.** `visitMemberSelect` deliberately did **not** walk into the receiver once it had rewritten a member of it, on the recorded assumption that "a further target cannot hide behind it". That is false: at `CombatAssistant:3285` the statement is

```java
PlayerHandler.players[c.playerIndex].underAttackBy != c.playerId
```

where `underAttackBy` and the nested `c.playerIndex` **are both ours**. The tool rewrote the member and returned without descending, so the nested `playerIndex` stayed bare and the class stopped compiling. **The bug is self-revealing** — the only way it can drop something is if that something was *also* moved, which cannot type-check — so no earlier pass could have been silently corrupted by it; every cluster compiled, and re-running all nine after the fix still reports **0 edits**, which independently proves none of the earlier passes hit the pattern. The fix removes the early `return` in both the `Rewriter` and the `Counter` (so counts and edits agree) and leans on the fact that `consider` is already name-gated, so a bare receiver like `c` in `c.playerLevel` still cannot be mistaken for a field. **The lesson is the general one: a tool's own comment is a claim to re-test, not documentation to trust** — and the compiler, not the dry run, is the backstop for an *incomplete* rewrite (the dry run's "every splice contains exactly the identifier it replaces" check only validates splices that were emitted).

**The index convention is 1-based with `0` as the sentinel**, so unlike the boolean bags this one's all-zero defaults are *load-bearing* rather than merely neutral: the guards branch on `> 0`, and a stray non-zero default would read as "already attacking slot N". `TargetingTest` pins the defaults, per-player ownership, and — reflectively, from both sides — that `NPC` still declares `underAttackBy` while `Player` no longer does.

`TargetingTest` (4). After the tool fix, re-running the tool reports **0 edits for all nine clusters**; `--fields` reports `declared fields : 616`. **240 tests green.**

## Phase 5 — Concurrency and service lifecycle  ✅ DONE

- ✅ **Replace the hand-wired tick loop with a proper scheduler.** `Server.main`'s `while (!shutdownServer) { sleep(600 - elapsed); ... }` is gone. The tick now runs on a single-threaded `ScheduledExecutorService` (`Server.startTicker`, thread `game-tick`, **non-daemon** — that thread is what keeps the JVM alive now, which is the one genuinely dangerous property of the change and was checked on a real boot). Each tick re-schedules the next for whatever is left of the budget (`sleepTime >= 0 ? sleepTime : cycleRate`), which is **start-to-start 600 ms while the server keeps up, and work + 600 ms on an overrun — exactly what the old `if (sleepTime >= 0) sleep(sleepTime); else sleep(600);` did**. Deliberately **not** `scheduleAtFixedRate` — a catch-up scheduler turns one slow tick into a burst, which for a game loop is a cascade. (⚠️ The first cut clamped the delay to `max(0, 600 - elapsed)`, which *did* catch up on an overrun and so reintroduced the very behaviour the design note rejected; caught on review and corrected, and the probe below confirms a 599 ms budget.) The ordered handler sequence is now `Server.tick()` with the reason for the order written once, and `runTick()` catches `Throwable` so a handler fault can never silently end the loop (with a self-rescheduling task, an escaping exception stops the game permanently while the server still looks alive).
  - ⚠️ **Behaviour change, deliberate:** an exception escaping `tick()` used to end the server after saving everyone (`catch` outside the `while`). It now logs and the loop continues. Per-player faults were already isolated per player.
- ✅ **The Mina↔game-thread boundary, made explicit.** The two real races were already fixed in Phase 0.2/0.5 and are now documented as the rule they are: I/O threads **enqueue** (`ConnectionHandler` → `Client.queueMessage` → a `ConcurrentLinkedQueue`) and the game thread **drains** (`PlayerHandler.process()` → `while (processQueuedPackets())`), with the only other cross-thread call (`newPlayerClient`) taking the `players` monitor for slot discovery + publication. ⚠️ **Not "enforced by the types", on purpose** — a wrapper interface would rename the same queue without preventing anything a reviewer cannot already see, so the rule is stated in `PlayerHandler`'s class doc and the boundary is covered by the concurrency-shaped tests instead.
- ✅ **Ordering guarantee — now a test, not a comment.** The per-player order was a comment beside one loop. `PlayerLifecycleTest.thePerPlayerTickRunsInItsDocumentedOrder` drives `PlayerHandler.process()` with a recording `Client` and asserts the exact sequence: `preProcessing → processQueuedPackets → process → postProcessing → getNextPlayerMovement → processCombatAfterMovement → initialize → clearUpdateFlags`. A reordering is invisible to the compiler, so this is the only thing that catches it.
- ✅ **Shutdown — a single lifecycle that saves everyone exactly once.** Three separate defects, all fixed:
  1. ⚠️ **Nothing was ever registered.** `server.ShutdownHook` and `core.util.ShutDownHook` both existed, both saved every player, and **neither was ever passed to `Runtime.addShutdownHook`** — the only reference to either was a commented-out line in `Server.main`. Both deleted; `Server.registerShutdownHook()` installs one hook whose body is the testable `Server.requestStop()`.
  2. ⚠️ **Every logout wrote the character file twice.** `PlayerHandler.process()` called `PlayerSave.saveGame(o)` and then `removePlayer(o)` → `Client.destruct()`, which saved again. (Phase 0.3 caught the two adjacent saves; this was the one straddling the call.) Fixed by making `Client.saveCharacterOnce()` the only final save, with a per-session guard, and deleting the save from the release path.
  3. ⚠️ **`destruct()` skipped the save for anyone in combat.** It opened with `if (underAttackBy > 0 || underAttackBy2 > 0) return;` and `if (session == null) return;` — and the update-kick path sets `kickAllPlayers`, which **bypasses the ten-second out-of-combat hold**, so a player fighting when the server restarted was dropped from the array with no character write and a leaked socket. Both early returns removed (the session is null-checked where used), and `destruct()` is now idempotent.
  - **Verified on a real JVM, not just in tests:** a boot reached `[Final Stage]`, `Server.main` returned and the JVM stayed alive on the ticker thread (sleep budget 0 → 599ms, i.e. ticks really are running), and a real `System.exit(0)` printed `[Shutdown] Saved 0 character(s).` — exercising `stopTicker()` against a **live** ticker, which no unit test can do. (`taskkill` without `/F` does *not* deliver a console event to a redirected process, so it is not a valid way to test this on Windows — record that.)
  - ⚠️ **Correction to an earlier claim in this file:** `saveTimer` was deleted on the reasoning that "`PlayerSaving` already saves every player every five minutes". **That was wrong.** `PlayerSaving.initialize()` had **no callers anywhere in the tree**, so its thread never started and its five-minute loop never ran. The deletion was still behaviour-neutral (`saveTimer` was write-only), but a character reached disk only on logout, on the drop/death/barrows paths that call `PlayerSave.saveGame` directly, or now on shutdown — **a crash or hard kill lost everything since the last logout.** Corrected in `Timers`' doc and `TimersTest`.
- ✅ **Follow-up: the periodic save, which did not exist.** The gap above is now closed. `PlayerSaving` was rewritten from a dead shell into a real autosave and wired into `Server.tick()`:
  - **It runs on the game thread, one character per tick.** The old design's fatal flaw was saving every player in a burst from its own background thread, reading live game state while the tick mutated it, and racing the logout path on the same client's file. Driving it from the tick removes all three: no locks, no races, no burst (under two writes a second even at 600 ms ticks), and it runs last in the tick so it never sees a player mid-update. ⚠️ **The cost, deliberate:** a character write happens on the tick thread, so a pathologically slow disk delays that one tick. That is why it is one character per tick and not a batch.
  - ⚠️ **The trap the design had to avoid, and the test that pins it:** the autosave must **not** latch `Client.saveCharacterOnce()`'s once-guard. If it did, the logout that followed would skip its save and the player would silently lose up to five minutes — a bug that reads as "the last few minutes don't stick". `PlayerSavingTest.anAutosaveDoesNotConsumeTheFinalLogoutSave` asserts the autosave leaves the flag alone *and* that a later logout's newer state is what lands on disk. An autosave followed by a logout therefore writes twice, on purpose.
  - The interval is five minutes, a full sweep is spread across as many ticks as it needs, mid-sweep calls ignore the interval (so sweeps never overlap), and an empty realm completes instantly rather than busy-looping. `Server.lastMassSave` — a `public static` field nothing ever read — was deleted with it, and the `sleepTime` javadoc that referenced the old `saveAllPlayers` was corrected.
  - **Verified on a live JVM:** a probe registers a stand-in logged-in player, back-dates the interval by reflection, and waits three seconds — the server prints `[Autosave] Saved 1 character(s).` and the file on disk contains the live position. That is what proves it is actually called from the tick, which no unit test can show.

## Phase 6 — Persistence and configuration

- **Externalise configuration.** `Config` is compile-time constants; credentials were hardcoded in source (`Server.java`'s `MainLoader` construction, `HiscoresHandler`'s IP/DB/user/pass). 🔄 **Credentials done in 6.1** — `server.Configuration` reads `Data/server.properties` (gitignored) with a checked-in `Data/server.properties.template`; the four hiscores values and the four vote values now come from it. ⚠️ **The design constraint that made it safe to land mid-verification: every getter takes a fallback and the call sites pass the exact literal that used to be there, so with no properties file the behaviour is bit-identical and copying the template verbatim is a no-op.** Remaining: the ~100 compile-time `Config` constants (server name, exp rates, teleport tables, item flags) — the same mechanism extends to them, but each needs a fallback that matches its current literal, and the `public static final` ones cannot be reassigned at runtime without losing their constant-folding (an int switch case, for instance, requires a compile-time constant), so this needs per-constant decisions rather than a sweep.
- **Fix the database layer.** ✅ **DONE (6.2, this session).** `HiscoresHandler`'s `public static Connection con` / `public static Statement stmt` are gone, replaced by **`server.util.ConnectionPool`** — a small dependency-free pool that validates each idle connection, bounds connect/socket time so a down database cannot stall a tick, and returns `null` instead of throwing. Every statement and result set is now closed, the name is bound as a parameter rather than concatenated, and the 24 per-save `UPDATE`s collapsed into one 49-placeholder statement. ⚠️ **Not yet run against a live `hs` table** — the schema was preserved column-for-column. `GTLVote`'s own connections remain inside its closed-source jar.
- **Password storage.** Save files hold unsalted `Misc.md5Hash(playerPass)` in plaintext, with a three-way legacy fallback on load accepting plaintext or `basicEncrypt`. Migrate to a salted hash (bcrypt/argon2) with a lazy upgrade path on login.
- **Save-file format.** Add a schema version header. Consider moving to a real format (JSON/SQLite) behind the same `PlayerSave` API, with a one-time importer from the flat-text files.
- **Charset.** `FileWriter` uses the platform default. Pin to UTF-8 explicitly — deliberately left out of Phase 0 because it changes output bytes.
